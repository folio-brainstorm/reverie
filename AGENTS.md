# AGENTS.md

This file applies to the entire repository. All new and modified code must follow these conventions. If a subdirectory contains a more specific `AGENTS.md`, the rules in the file closest to the target file take precedence.

## Project Overview

- This repository is a TypeScript ESM monorepo managed with pnpm.
- `core/`: The core drawing engine package, using TypeScript `NodeNext` module resolution.
- `demo/`: The React + Vite demo application.
- `test/`: The Vitest test package.
- Use the Node.js and pnpm versions declared by the repository. Do not mix npm or Yarn into the workflow, and do not commit lockfiles generated by other package managers.

## General Principles

- Prioritize correctness, readability, and maintainability. Avoid speculative abstractions, overengineering, and implicit side effects.
- Each file must have one clear responsibility. An implementation file should generally define only one primary class, component, or function.
- Keep changes focused on the current task. Do not refactor unrelated code or alter public behavior outside the requested scope.
- Prefer existing modules and utilities. Extract a shared abstraction only when it has multiple real consumers or meaningfully reduces complexity.
- Do not use `any`, unnecessary type assertions, `@ts-ignore`, or disabled compiler checks to bypass type errors. If an exception is unavoidable, document the reason and limit its scope as much as possible.
- Remove unused code, unused imports, debug logging, and commented-out legacy implementations. Do not retain code merely because it might be useful later.

## Files and Exports

- Each implementation file may contain at most one `export default`, and it must represent the file's single primary entity.
- Do not place multiple unrelated exports in one file. Keep helpers private by default; move them into separate files only when they need to be reused.
- Use `index.ts` only as a public API aggregation point. Do not place business logic in it. Index files may use named re-exports and are not required to provide an `export default`.
- Do not create broad global barrel files that expose internal implementations. Use `index.ts` only at explicit module boundaries or package entry points.
- Preserve the existing ESM convention: relative imports within `core/` must include the emitted `.js` extension, for example `import Foo from "./Foo.js"`.
- Import from another package through its public entry point. Do not reach across packages into another package's `src/` directory. If a test genuinely needs an internal implementation, prefer exposing it through an explicit public or test-only entry point.
- Dependencies used only as types must use `import type` or `export type` to avoid unnecessary runtime dependencies.
- Any addition, removal, or signature change to a public API must be reflected in the package entry point, tests, and relevant documentation.

## Type Organization

- All handwritten `interface`, `type`, and `enum` declarations, as well as contracts that contain type information only, must live in the `interfaces/` directory of the relevant package or application.
- Organize types by domain, for example:
  - `core/src/interfaces/world/`
  - `core/src/interfaces/pixel/`
  - `core/src/interfaces/tile/`
  - `demo/src/interfaces/`
- Do not collect every type in a single `types.ts` or root-level `interfaces.ts` file. Directory and file names must communicate their domain and responsibility.
- Each type file should center on one primary concept. Types may share a file only when they are tightly coupled and are always used together.
- Type files must not contain runtime logic, mutable state, or side-effectful initialization. Place runtime constants and implementations in the relevant `config/`, `utils/`, or domain module.
- Prefer `interface` for extensible object contracts. Use `type` for unions, intersections, mapped types, conditional types, and template literal types. Do not mechanically convert between them merely for stylistic consistency.
- Do not redeclare equivalent types. Import and reuse the type owned by the appropriate domain module.
- Public functions, class members, and component props must have explicit types. Local variables that TypeScript can reliably infer do not require redundant annotations.
- Do not use wrapper object types such as `String`, `Number`, or `Boolean`; use `string`, `number`, and `boolean` instead.

## Functions, Classes, and Components

- Every exported function must have meaningful JSDoc. This includes directly exported functions, functions exported from namespaces, public callback factories, and public class methods.
- JSDoc must explain purpose and behavior rather than repeat the function name. Include the following tags when relevant:
  - `@param`: Parameter meaning, units, valid ranges, or special values.
  - `@returns`: The meaning of the return value and any important constraints.
  - `@throws`: Errors that may be thrown and the conditions that trigger them.
  - `@example`: Include an example when usage is not obvious, boundary behavior matters, or the function is part of the public API.
- Do not commit empty JSDoc such as `/** */` or comments that contain only placeholder text.
- Non-exported functions should also have JSDoc or an explanatory inline comment when they contain complex behavior, mathematical constraints, edge cases, or important design tradeoffs.
- Keep functions small and focused on one task. Use early returns to reduce nesting, and extract complex conditions into clearly named Boolean variables or helper functions.
- Public functions must declare explicit return types. Async functions must use `Promise<T>`; do not rely on inferred return types for public APIs.
- Do not mutate function parameters. If in-place mutation is required for a measured performance goal, make it explicit in the name, JSDoc, and tests.
- Classes must have a single responsibility. Prefer `private` for internal state and avoid publicly mutable fields.
- Use function components and Hooks for React code. Place component prop types in the appropriate domain directory under `demo/src/interfaces/`; do not declare ad hoc exported prop types in component files.
- Call Hooks only at the top level of a component or custom Hook. Do not call them inside conditions, loops, or nested functions.

## Naming and Formatting

- Name files after their primary export. Use `PascalCase.ts(x)` for classes, React components, and type files. For ordinary function files, follow the existing project convention and remain consistent within the directory.
- Use `PascalCase` for classes, components, interfaces, type aliases, and enums.
- Use `camelCase` for functions, methods, variables, and object properties.
- Use `UPPER_SNAKE_CASE` for genuine module-level constants that are never reassigned. Do not force ordinary local `const` variables to use uppercase names.
- Prefix Boolean values with words that communicate a predicate, such as `is`, `has`, `can`, or `should`.
- Avoid obscure abbreviations and single-letter names, except for conventional loop indexes or mathematical variables.
- Follow the existing formatting style: double quotes, semicolons, trailing commas, and two-space indentation. Do not modify unrelated lines solely to apply formatting preferences.
- Group imports in the following order, separated by blank lines: third-party packages, workspace packages, package-internal absolute paths if applicable, relative paths, and styles or other side-effect imports.

## Error Handling and Logging

- Validate external input and public API boundaries. Do not repeat defensive validation for values already guaranteed by the type system or an upstream invariant.
- Use the project's existing error types and error definitions. New errors must have a stable identifier, clear context, and corresponding tests.
- Do not swallow exceptions. After catching an exception, either recover, convert it into a more meaningful error, or add necessary context and rethrow it.
- Do not use `console.log` casually in library code. Use `console.warn` or `console.error` only when the caller genuinely needs to be informed and throwing an error would be inappropriate.
- Error messages must be actionable and include enough information to diagnose the problem, but they must not expose secrets, tokens, user data, or large amounts of raw input.

## Testing Requirements

- Every bug fix must include a regression test that fails before the fix and passes afterward.
- New public behavior must cover at least the happy path, boundary conditions, and failure paths. Numeric logic involving coordinates or dimensions must explicitly cover zero, negative values, boundaries, and invalid values.
- Test observable behavior rather than private implementation details. Test names must clearly describe the scenario and expected outcome.
- Prefer parameterized tests with `it.each` when multiple inputs exercise the same rule.
- Tests must be deterministic, isolated, and independent of execution order, real networks, the current time, or local machine state. Use controllable mocks or fakes when such dependencies are necessary.
- Do not use snapshots in place of precise business assertions.
- After changing code, run at least the type checks and tests for the affected package. Run the complete root-level checks for cross-package or public API changes.

## Validation Commands

When a change adds or updates workspace packages or dependencies, run only the
following commands in order instead of expanding them into package-level install,
build, typecheck, or test command sequences:

```bash
pnpm install
pnpm test
```

Treat `pnpm test` as the primary validation entry point for this workflow. Only
run additional diagnostic commands when one of these commands fails and the
extra command is needed to identify the cause.

Run these commands from the repository root:

```bash
pnpm typecheck
pnpm test
pnpm build
```

During development, smaller checks may be run first:

```bash
pnpm --filter @reverie/core typecheck
pnpm --filter @reverie/demo typecheck
pnpm --filter @reverie/test test
```

If an environmental limitation prevents a validation step from running, list the skipped command and the reason in the final delivery notes. Do not claim that validation passed when it was not run.

## Pre-Submission Checklist

- Does each file have one clear responsibility and at most one `export default`?
- Are all new types located in an appropriately categorized `interfaces/` directory?
- Do all exported functions and public methods have complete, non-placeholder JSDoc?
- Are type-only imports using `import type`, and are the ESM and `.js` extension conventions followed?
- Does the change avoid `any`, unjustified assertions, swallowed exceptions, and cross-package internal imports?
- Are public APIs, types, entry-point exports, documentation, and tests synchronized?
- Are the happy path, boundary conditions, and error cases covered, and have the appropriate type checks, tests, and builds been run?
